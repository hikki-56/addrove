# ผลตรวจความช้าก่อนแก้จุดคอขวดของระบบพนักงาน

วันที่ 12 ตุลาคม 2026 — ทดสอบโค้ดในเครื่องที่ยังไม่ได้ push/deploy ตามที่ผู้ใช้แจ้ง

เอกสารนี้เก็บผลรอบก่อนแก้คอขวด ส่วนไฟล์ JSON ที่กล่าวถึงด้านล่างถูกรันและเขียนทับด้วยโค้ดหลังแก้แล้ว ดูผลล่าสุดและเงื่อนไข deploy ใน `employee-performance-report.md`

ชุดทดสอบผ่าน **135 profiles**: โหลดข้อมูลหน้า 12, callback รับเข้า/สแกน/ยืนยันเบิก 19 และ service รับเข้า/เบิก 104 พร้อมตรวจข้อผิดพลาด การยกเลิกคำขอ การกดซ้ำ และสต็อกไม่พอ

การรับเข้าและเบิกทั้งหมดใช้ข้อมูลสร้างใหม่ในหน่วยความจำและ HTTP จำลอง ไม่เปิดหรือแก้รายการเดิมในเว็บจริง ไม่เชื่อม Google Sheets และไม่มีการบันทึกธุรกรรมจริง

## จุดรอที่พบ

### 1. สแกนตำแหน่งต้นทางหนึ่งครั้ง ดึงสินค้าทั้งโกดังหนึ่งครั้ง

`handleVerifySourceLocationBarcode` ใน `src/features/transfer/hooks/use-transfer-movement.ts` เรียก `/api/products?warehouse_id=...` ทุกครั้งที่ตรวจตำแหน่งต้นทางสำเร็จ จึงสะสมเวลารอตามจำนวนตำแหน่งที่สแกน

ผลเรียก callback จริงกับข้อมูล/HTTP จำลอง ปริมาณ 1 ชิ้นต่อตำแหน่ง:

| ตำแหน่งที่สแกน | คำขอสินค้า | เวลารวมจำลอง |
| ---: | ---: | ---: |
| 1 | 1 | 9.47 ms |
| 10 | 10 | 159.74 ms |
| 50 | 50 | 775.90 ms |
| 100 | 100 | 1,531.10 ms |

เพิ่มเป็น 1,000 ชิ้นต่อตำแหน่งยังเกิดคำขอเท่าเดิม; 100 ตำแหน่งใช้ 1,545.24 ms ในรอบนี้ ปัจจัยที่ชัดคือจำนวนครั้งที่สแกนและขนาดข้อมูลสินค้า ไม่ใช่การวนทำงานทีละชิ้น

แนวทางลดงาน: ดึงเฉพาะ SKU/ตำแหน่งที่กำลังตรวจ หรือใช้ข้อมูลที่โหลดไว้ร่วมกันระหว่างสแกน พร้อมตรวจสต็อกล่าสุดที่ server ตอนยืนยัน ต้องคงความถูกต้องเมื่อหลายคนทำงานพร้อมกัน

### 2. ก่อนส่งคำขอยืนยันเบิก รอการบันทึกขั้นตอนเดิมได้ถึง 8 วินาที

`handleSubmitTransfer` รอ `whenTransferProgressSettled` ผ่าน `Promise.race` กับ timeout 8,000 ms ก่อน POST `/submit`

| การบันทึกขั้นตอนที่จำลอง | รอก่อนเริ่ม POST ยืนยัน | เวลารวม callback |
| --- | ---: | ---: |
| ไม่มีคำขอค้าง | 0.37 ms | 33.00 ms |
| หน่วง 250 ms | 261.44 ms | 292.19 ms |
| หน่วง 8,500 ms | 8,012.65 ms | 8,044.04 ms |

กรณีสุดท้ายจำลองอาการกดยืนยันแล้วรอประมาณ 8 วินาทีก่อนเริ่มส่งคำขอยืนยันได้จริง การรอนี้ช่วยจัดลำดับการเขียนข้อมูล; การตัดออกทันทีอาจทำให้ progress เก่าทับสถานะใหม่ แนวทางแก้ที่ควรพิจารณาคือรวมการบันทึกขั้นตอนกับการยืนยันใน server operation เดียว หรือลด progress write ที่ซ้ำ พร้อมทดสอบ race ก่อนเปลี่ยน

### 3. หน้าโหลดข้อมูลรอ endpoint ที่ช้าที่สุด และยังโหลดสินค้าทั้งโกดัง

ทดสอบ `useWarehouseData.refreshData` จริง โดยจำลองสินค้า 10 / 1,000 / 10,000 แถว และ endpoint ตำแหน่งปกติ/ช้า

เมื่อจำลอง locations หน่วง 150 ms และสินค้า 1,000 แถว:

| รูปแบบการโหลด | คำขอ | median ข้อมูลพร้อมใช้ |
| --- | ---: | ---: |
| รับเข้า/ย้าย โหลด locations | 3 | 160.11 ms |
| หน้าพนักงานเบิก ตั้ง `loadLocations: false` ตามโค้ดที่แก้ในเครื่อง | 2 | 22.77 ms |

ผลนี้ตรวจว่าหน้าเบิกตัดคำขอ locations ที่ไม่ใช้ใน initial load ได้ ไม่ใช่ผลก่อน/หลัง deployment จริง การโหลดสินค้า 10,000 แถวมี response จำลองประมาณ 2.03 MB; ค่าเวลาที่ใช้ HTTP จำลองไม่ได้สะท้อนเวลาส่งข้อมูลจริงผ่านอินเทอร์เน็ต

### 4. รับหลายรายการไม่ได้สร้างคำขอทีละชิ้น แต่ยังมีการอ่านข้อมูลและรอ lock

callback รับเข้า 1 / 10 / 50 / 100 รายการ ปริมาณ 1 / 1,000 ชิ้นต่อรายการ ส่ง POST รับเข้า **ครั้งเดียว** ทุก profile ในรอบนี้ใช้ 23.75–31.54 ms เมื่อจำลอง API หน่วง 20 ms การ refresh หลังรับเข้านับว่าถูกเรียก แต่ไม่นับเวลารอ refresh เพราะ callback ไม่ await งานนี้

service ใช้ implementation จริงกับ repository ในหน่วยความจำ ทดสอบข้อมูลขนาดเล็ก (ประวัติ 100 / สินค้า 100 / ตำแหน่ง 100 แถว) และใหญ่ (ประวัติ 25,000 / สินค้า 5,000 / ตำแหน่ง 2,000 แถว) พร้อมการรับตามแผนและการทำงานพร้อมกัน

ตัวอย่างผลจำลอง repository หน่วง 5 ms ต่อ top-level method:

| งาน | median ตอบกลับจำลอง |
| --- | ---: |
| รับเข้า 1 รายการ ข้อมูลเล็ก | 76.01 ms |
| รับเข้า 100 รายการ ข้อมูลเล็ก | 77.27 ms |
| รับเข้า 100 รายการ ข้อมูลใหญ่ ปริมาณ 1 ชิ้น | 70.30 ms |
| รับเข้า 100 รายการ ข้อมูลใหญ่ ปริมาณ 1,000 ชิ้น | 75.87 ms |
| รับตามแผน 100 รายการ ปริมาณ 1 ชิ้น | 137.06 ms |
| พนักงานยืนยันเบิก 100 งานทีละงาน | 1,549.67 ms รวม / 15.50 ms ต่องาน |

จำนวนชิ้นเพิ่มไม่ได้ทำให้เวลาขยายตามจำนวนชิ้นในชุดนี้ และผลข้อมูลใหญ่ไม่ได้ช้ากว่าเสมอ จึงยังใช้ตัวเลขนี้จัดอันดับผลกระทบของประวัติจริงไม่ได้ การรับตามแผนมีงานตรวจ/เขียนเพิ่ม และการรับพร้อมกันที่ใช้ stock key เดียวมีการรอ lock; รายละเอียดเวลา lock และ method อยู่ใน JSON

การสร้างงานเบิกฝั่ง admin แยกเป็น supporting profiles เพื่อดู fan-out/ข้อจำกัด concurrency ไม่รวมความหมายว่าเป็นเวลาเบิกหนึ่งงานของพนักงาน

## ความถูกต้องที่ตรวจแล้ว

- รับเข้าได้เอกสาร `PENDING`; ยืนยันเบิกได้ `WAITING_APPROVAL` ตาม flow ก่อนผู้อนุมัติ สต็อกยังไม่เปลี่ยนในขั้นตอนเหล่านี้
- ส่งคำขอเดิมซ้ำไม่สร้างเอกสารซ้ำ; รับเข้าพร้อมกันด้วย idempotency key เดียวไม่เกิดรายการซ้ำ
- สต็อกไม่พอถูกปฏิเสธโดยไม่มีเอกสารหรือการเปลี่ยนสต็อกเพิ่ม
- รับตามแผนตรวจยอดสะสมตามข้อมูลจำลอง
- โหลดข้อมูลผิดพลาดปลด loading และแสดง error; response ที่ยกเลิกไม่ทับคำขอใหม่

## เว็บจริงและข้อจำกัด

เปิดเว็บจริงด้วยบัญชีพนักงานและตรวจการนำทางแบบอ่านอย่างเดียว ไม่เปิดงานเดิมและไม่กดบันทึกรับเข้า/เบิก เว็บจริงยังเป็นเวอร์ชันก่อนการแก้ในเครื่องตามที่ผู้ใช้แจ้ง

การวัด HTTP สาธารณะ 3 รอบจาก URL dashboard ได้ redirect ไปหน้า login รวม 704.03 / 316.78 / 288.72 ms ตัวเลขนี้เป็น **การอ่านหน้า login รวม redirect แบบยังไม่ได้ยืนยันตัวตน** ไม่ใช่เวลา Dashboard, API สต็อก หรือเวลา render ของพนักงาน ไม่สามารถเก็บ browser performance ของหน้าที่ login แล้วอย่างน่าเชื่อถือในรอบนี้

ชุดหลักใช้โค้ดจริงที่ transpile แล้วกับ boundary จำลอง ไม่ใช่ browser E2E ทั้งระบบ ไม่มีเวลาของ React render, auth/proxy, Google Sheets, cold start, retry เครือข่าย หรือเครื่องสแกนจริง การจับเวลาหน่วง 5 ms บนเครื่องนี้เกิด median 15.405 ms จาก timer/OS scheduling จึงต้องดูจำนวนคำขอและลำดับการรอประกอบ ตัวเลขทั้งหมดไม่ใช่ SLA หรือ production p95

หน้าโหลดข้อมูลเก็บ 3 ตัวอย่างต่อ profile, client callback 1 ตัวอย่างหลัง warm-up และ workflow 2 ตัวอย่างต่อ profile เวลา method อาจทับซ้อนกัน ห้ามบวกเป็นเวลารอผู้ใช้; `activeElapsedMs` รวม injected wait ของ method นั้นแล้ว

ชุด benchmark รันผ่าน แต่ยังไม่ยืนยัน Jest/lint/typecheck ของทั้งโครงการ เพราะ dependencies ใน `node_modules` ไม่ครบตามที่ตรวจไว้ก่อนหน้า

## รันซ้ำและไฟล์ผล

รันชุดจำลองทั้งหมด (ไม่มี network หรือธุรกรรมจริง):

```sh
npm run test:employee-performance
```

รันแบบเร็ว ลดจำนวนตัวอย่าง workflow/page และข้ามกรณีรอ 8 วินาที:

```sh
npm run test:employee-performance -- --quick
```

ไฟล์ผลจะถูกเขียนทับเมื่อรันใหม่:

- `artifacts/performance/employee-page-load-benchmark.json`
- `artifacts/performance/employee-client-action-benchmark.json`
- `artifacts/performance/employee-workflow-benchmark.json`

การอ่าน HTTP สาธารณะเป็นคำสั่งแยกและไม่อยู่ใน npm runner:

```sh
node scripts/performance/employee-live-read-benchmark.mjs --url="https://addrove.vercel.app/dashboard?warehouse_id=wh-01"
```

ผลอยู่ใน `artifacts/performance/employee-live-read-benchmark.json` คำสั่งนี้ใช้ GET แบบไม่มี credentials และไม่บันทึกธุรกรรม

รายงานนี้ไม่ได้ยืนยันว่าการลดโหลดที่แก้ในเครื่องขึ้นเว็บจริงแล้ว ยังไม่มี commit/push/deploy จากงานนี้
