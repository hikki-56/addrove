# ตรวจสอบความช้าในงานรับเข้าและเบิกสินค้า

วันที่: 10 ตุลาคม 2026

ตรวจจากโค้ดและชุดทดสอบในเครื่อง ยังไม่มี production trace หรือเวลาตอบสนองจริง จึงยังระบุไม่ได้ว่าจุดใดเป็นสาเหตุหลักของเหตุการณ์ที่พนักงานรายงาน

## จุดที่พบและแก้ไข

- `use-warehouse-data.ts`: คำขอโหลดโกดัง/ตำแหน่ง/สินค้าไม่มี timeout และไม่มีการยกเลิกคำขอเก่า เมื่อเปลี่ยนโกดังหรือรีเฟรชซ้อน คำตอบเก่าอาจทับข้อมูลใหม่ แก้ด้วย AbortController, timeout 30 วินาที และตรวจว่าคำตอบมาจากคำขอปัจจุบันก่อนอัปเดต state
- HTTP error เดิมถูกแปลงเป็นรายการว่าง ทำให้ผู้ใช้แยกไม่ออกว่าโหลดล้มเหลวหรือไม่มีสินค้า แก้ให้แสดงข้อผิดพลาดและปุ่มลองโหลดใหม่ในหน้ารับเข้าและโอนสินค้า
- การกู้คืนร่างรับเข้าเดิมค้นสินค้าทีละรายการ และอัปเดต products ระหว่าง loop ทำให้ effect ยกเลิกแล้วเริ่มใหม่ แก้ให้อ่าน master ครั้งเดียว จับคู่แบบตรงรหัส และรวม state update ครั้งเดียว พร้อมยกเลิกคำขอเมื่อ effect เปลี่ยน
- `receive-stock.ts`: อ่านสินค้าและตำแหน่งตามลำดับทั้งที่เป็นอิสระ แก้ให้อ่านพร้อมกัน โดยคงการตรวจแผน ตำแหน่ง และ idempotency

## จุดที่ควรวัดจากระบบจริงก่อนปรับเพิ่มเติม

- `/movements/issue` redirect ไป `/movements/transfer` จึงต้องเก็บเวลาของงานโอนและงานพนักงานที่เกี่ยวข้องด้วย รวมถึง `/api/movements/issue` หากมีผู้เรียกใช้
- งานรับเข้าตรวจเอกสารย้อนหลังสูงสุด 9,999 รายการเพื่อกันรายการซ้ำ ต้นทุนเพิ่มตามประวัติเอกสาร ควรพิจารณา index สำหรับ idempotency ที่คงความถูกต้องข้าม instance
- งานเบิกตรวจยอดแต่ละบรรทัดและซิงก์แท็บโกดังตามลำดับ การเพิ่มจำนวนรายการเพิ่มจำนวนรอบ I/O การเปลี่ยนเป็น batch ต้องคงการล็อกและตรวจยอดรวมของสินค้าซ้ำ
- การอ่าน Google Sheets มี retry และ fallback หลายทาง เมื่อบริการต้นทางช้าหรือถึง quota อาจทำให้รอนาน การตัดคำขออ่านฝั่งหน้าเว็บไม่ได้หยุดการประมวลผลฝั่ง server
- หน้างานโอนโหลดสินค้าต้นทางเพิ่มเติมจาก hook ของตัวเอง ควรวัดคำขอซ้ำและความสดของข้อมูลก่อนรวมแหล่งข้อมูล

## การแก้ไขเพิ่มเติม

- งานเบิกจัดกลุ่มสินค้า/ตำแหน่งซ้ำและตรวจยอดรวม ป้องกันหลายบรรทัดใช้ยอดคงเหลือเดิมจนเบิกเกินยอด อ่านยอดครั้งเดียวต่อกลุ่ม และอ่านพร้อมกันสูงสุด 4 กลุ่มก่อนเริ่มเขียน
- ซิงก์การเบิกสินค้า/ตำแหน่งซ้ำครั้งเดียวต่อกลุ่ม โดยคง movement แต่ละบรรทัดและ idempotency key เดิม
- ตรวจ idempotency ของเอกสารใน Sheets โดยตรง ไม่สร้าง Document object ทั้งชุด และไม่จำกัดตรวจเฉพาะ 9,999 รายการ ยังอ่านชีตทั้งหมดอยู่ ไม่ใช่ distributed index
- หน้างานโอนใช้รายการสินค้าที่โหลดแล้วเมื่อโกดังต้นทางตรงกับโกดังปัจจุบัน ยกเลิกคำขอต้นทางเก่าและตัดเวลารอ 30 วินาทีเมื่อโหลดโกดังอื่น
- หน้าโอนของพนักงานแสดงข้อผิดพลาดการโหลดพร้อมปุ่มลองใหม่
- การอ่าน HTTP/Google Sheets API แต่ละคำขอมี timeout 10 วินาที รวมการอ่าน metadata และ batch read โดยไม่เพิ่ม timeout ในคำสั่งเขียนสต็อก ทั้งเส้นทางยังอาจใช้เวลามากกว่านี้เพราะ retry/fallback

เก็บ Network timing และ server logs ของพนักงานช่วงเกิดอาการ พร้อมเส้นทางหน้า จำนวนรายการในเอกสาร และเวลารอ Google Sheets/lock แยกเวลาตอนเปิดหน้า สแกน และส่งรายการ เปรียบเทียบ p50/p95 ก่อนและหลังในช่วงโหลดใกล้เคียงกัน ไม่สรุปตัวเลขความเร็วจาก unit tests

Timeout ที่เพิ่มใช้กับการอ่านข้อมูลเท่านั้น ไม่ยกเลิกการบันทึกสต็อกกลางทาง ซึ่งอาจทำให้ผู้ใช้ไม่ทราบว่ารายการบันทึกสำเร็จแล้วหรือยัง
